# Strict Doctrine Index

The complete pre-tier doctrine is preserved in
`strict-doctrine-reference.md`. Open only the paragraph or section matching the
active incident.

| Incident | Search phrase in strict reference |
| --- | --- |
| Failed visible or interactive proof | `User-facing verification is the acceptance surface` |
| User says the same bug remains | `If a user reports that the same UI/rendering/control bug` |
| Repeated focused fixes | `Hard realignment rule` |
| Long red acceptance lane | `Long-lane acceptance and cutover gate` |
| Speculative visual tuning | `Bounded visual parameter tuning` |
| User-facing parameter closure | `Parameter surface closure is mandatory` |
| UI control wiring | `Product-facing UI controls also require live mutation proof` |
| Standardized format or protocol | `For standardized file formats` |
| Known-good regression path | `ask the regression question` |
| GPU capability downgrade | `Treat GPU feature capability failures as hypotheses` |
| Full-quality performance | `preserve the full-quality target` |
| Viewport or stroke replay | `Stroke-like UI proof must be a human-input session` |
| Stale launcher or binary | `User-facing launch path is part of visible proof` |
| Code-map drift | `Treat code-map maintenance as an ordinary source-edit closeout gate` |
| External runtime mismatch | `mutable external runtime copy` |
| Review or worker evidence | `When supervising a worker, do not judge` |
